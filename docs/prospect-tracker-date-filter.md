# Prospect Tracker date filtering — Issue #28

[Issue #28](https://github.com/rainbows4dinos/nextchapter/issues/28) is implemented locally on top of [Automatic Applied Date](prospect-tracker-applied-date.md). No database migration, new dependency or production change is required. The original feature was deployed on October 18, 2026; the October 19 frontend release includes filtered reordering.

## Controls and date meaning

The page header places **Add Prospect** opposite the title/description, above a divider. The board toolbar keeps **Prospects (count)** left and search, current status and one calendar/date trigger right. A secondary-text results count appears inline immediately before Search only when fewer than all loaded prospects are visible, as `12 of 63` or `0 of 63`. Filters that retain every result show no redundant count. History-incomplete warnings remain separate. The existing cards, responsive board and collapsible Done column are preserved.

The date trigger defaults to **All dates**, with Added as the initial basis. Active labels show both basis and range, such as **Applied: Last 90 days**; custom labels show human-readable calendar dates, with years for past/future years and both endpoints when crossing a year. A single nonmodal popover contains a compact native-radio segmented control for **Date type** (Added / Applied) and radio choices for **Date range** (Last 7/30/90 days, Last year, Custom range, All dates). No native date select menus or Apply button are used. Existing Gravity calendar/plus icons and shared control/theme tokens are reused.

Presets apply immediately and retain the chosen basis. Custom exposes native calendar-date inputs inside the popover. Both endpoints must be valid and ordered before changing the active range. Incomplete/invalid drafts show feedback while the last valid range remains active; changing type still changes only the basis. All dates clears the restriction and custom draft dates while retaining basis, search and current status. Escape restores trigger focus; native light dismissal handles outside clicks. Radio arrows, Tab and visible focus styles support keyboard use. Popover listeners close/clean up on route disposal and use no prospect persistence.

Past N days includes today and the preceding N−1 local days. Past Year starts on the same calendar day in the previous year, clamping February 29 when necessary, and ends today. Timestamp filtering uses local midnight at the start and next-day exclusive midnight at the end, respecting daylight-saving changes. `applied_on` remains a date-only value and never shifts through UTC.

- **Added date** uses `created_at` explicitly. It describes adding a record, not submitting an application. `updated_at` is never a date basis.
- **Applied date** prefers the saved `applied_on`, including manual corrections and backdated dates, regardless of current status.
- When that field is missing, the first genuine historical transition into Applied supplies a fallback. It must have a non-null, different `from_status`; an initial Applied import/creation event does not qualify. Repeat transitions do not duplicate a card or replace the first fallback.
- Fallback cards visibly say **Applied status recorded [date]**. This records a status action, not proof of actual submission. The UI asks the user to review/correct the application date before reporting. No inferred date is written back.
- Records with no qualifying date are excluded from bounded Applied ranges. Applied / All keeps them accessible and labels **Application date unknown**. An unavailable history read is labeled incomplete rather than treating missing history as confirmed absence.

The date predicate itself never requires current status Applied; an independently selected current-status filter can narrow those matches. Interviewing, rejected, withdrawn and other prospects remain in their existing lifecycle columns when their application date matches. Matching Done cards open through the existing disclosure when the filter changes or history becomes available; its matching count remains visible.

## Ordering, state and reads

Search, current-status and date filtering compose with AND after manual column ordering. Existing company/title search semantics remain. Counts show the matching total and per-column X of Y; empty columns distinguish no matches, invalid dates and incomplete history. All plus an empty search restores the underlying full manual order. Within-column native drag and Alt+Up/Down reordering work with every search/date combination. Only visible cards exchange their existing slots in the full column order; hidden cards retain their indices. Saves submit the complete column order to the existing guarded RPC. Keyboard steps skip hidden cards, and first/last visible boundaries are no-ops. Existing cross-column status actions remain available.

The controls and scroll containers stay mounted during changes. Query, current status, basis, preset and valid custom dates survive opening a card and returning in the same application session. This follows the existing in-memory board state; a full page reload resets filters, and owner/session changes discard state. There is no additional browser storage of prospect/history data.

Applied history loads lazily when selecting Applied basis. The dedicated `listAppliedTransitions(signal)` data method selects only genuine Applied transitions under the existing history RLS, paginates in 500-event batches, and uses timestamp/ID ordering. Requests scale by pages rather than prospects. A page failure rejects the whole load; the board shows incomplete results and Retry history, preserving filters. Known explicit-date matches can remain visible, with the count clearly marked incomplete. Disposing the board aborts the read and prevents late responses repainting another route/session. Successful history is cached only while that board view is mounted and re-read on return from Details.

Filtering makes no prospect, status, application-date or ledger writes. It reuses Issue #16's local calendar helper and the existing append-only history. No reporting/export flow, benefits submission, backfill or Résumé Builder change is added.
